# M11.4 多路径补齐的衡量

脚本：`tools/multipath_check.py`（R85、R86）、`tools/android_multipath.py`（R87、R88）。2026-11-25。

两台机器：开发容器（内核没有 netem，链路没有额外延迟，tbf 限速）；用户的云端 Linux 机器（Ubuntu 内核 6.8，有 netem）。
两条 veth 链路各限速 20 Mbit/s。都用 release 构建。

## 批量（R85）

「只有一条」= link2 标为计费时取 16 MB（批量只走 link1）；「两条」= 改回自动识别后紧接着取 16 MB，**第一次就算**，不预热。

| 条件 | 只有一条（Mbit/s） | 两条，第 1 / 2 / 3 次（Mbit/s） | 倍数（第 1 次） |
| --- | --- | --- | --- |
| 改之前，20 毫秒往返 | 11.5、17.9、17.9 | 11.3、35.5、35.0 | 0.6 |
| 改之前，20 毫秒往返（再一次） | 9.6 起 | 9.6、18.4、18.3（link2 几乎不用） | 0.5 |
| 改之后，没有延迟 | 18.8–18.9 | 37.6、37.7、37.6 | 2.00 |
| 改之后，20 毫秒往返 | 17.8–18.3 | 35.7、35.4、34.3 / 35.1、35.0、35.4 | 1.95–1.98 |
| 改之后，5 毫秒和 40 毫秒（两条延迟不同） | 18.0–18.4 | 35.0、35.9、35.2 | 1.93 |

（M5 记录的「1.5 倍」是三次里取最好的；稳态本来就接近两倍，差在开头。）

**原因**：BBR 的「应用受限」标记在上一段受限的数据刚送达的那次确认里被清掉，即使这时仍然没有数据可发，也不再重新标记
（`else if`）。终端每 20 毫秒一行、每秒一次心跳这类零星流量于是被当成「带宽已经到顶」的测量：BBR 在第 14 个往返就退出起步阶段，
带宽估计停在 127 KB/s（日志 `DBG drain max_bw=127477`），之后的批量传输在 ProbeBW 里要好几秒才涨上去；
刚从计费改回不计费的路径更糟，估计停在几 KB/s，整次传输几乎不用它。改成清掉之后照样检查一次，
零星流量的测量都标为受限，起步阶段一直留到真正的批量传输来测带宽。

## 经中继的路径（R86）

home 上的中继（`cargo build --example local_relay -p nexus-fabric-iroh`），laptop 经 link1 的 TCP 连到它；
丢弃两条链路上的所有 UDP（直连都断，中继可达）。`nexus exec` 每 20 毫秒一行。

| 条件 | 改之前 | 改之后 |
| --- | --- | --- |
| 直连都断时输出的最长停顿（没有延迟） | 8.0 / 5.1 / 23 秒（三次） | 0.03–0.08 秒（六次） |
| 直连都断时输出的最长停顿（20 毫秒往返，云端机器） | — | 0.10 / 0.77 / 2.3 秒（三次） |
| 直连都断时经中继取 4 MB | 成功 | 成功（不限速 600 Mbit/s 以上；限速时 17–18 Mbit/s） |
| 恢复 UDP 后重新有两条直连路径 | 0.3 秒 | 0.3–0.7 秒 |
| 恢复后取 4 MB 经中继的比例 | 0% | 0–0.1% |

**原因**：中继路径一直开着（Backup），直连都可疑时新数据本来就可以走它，但已经发到直连路径上、还没确认的数据
只在「还有别的健康的 Available 路径」时才马上转走；直连都断时没有这样的路径，这些数据要等直连路径 5 秒没有回应被放弃后
才在中继上重发。改成 Backup 路径（中继、计费的接口）也算健康路径。

有延迟时停顿长短不一：中继路径平时只有心跳，往返时间的估计不准，接手数据后偶尔自己也超时一次（日志里中继路径的 `PTO fired`），
这期间没有健康的路径。上限 3 秒（FP-11.4-02）都满足；要再缩短需要让空闲的中继路径保持更准的往返时间估计。

## 回归（M5 的检查）

改之后在开发容器里：故障转移最长停顿 0.03–0.05 秒；一条链路丢 30% 时终端（冗余）最长间隔 27–40 毫秒、exec 75–86 毫秒；
计费的链路承担批量 0.0–0.5%。云端机器（20 毫秒往返）：故障转移 0.03–0.06 秒，计费 0.0%。
（云端机器的 iptables 没有 statistic 模块，丢包的冗余检查只在开发容器里做。）

## Android（R87、R88）

`tools/android_multipath.py`，云端机器上的 redroid（Android 13，x86_64，docker 桥接网络）。redroid 的网络命名空间里两条 veth
（nxl1、nxl2）连到另一个命名空间里的 home。一次全部通过：

| 项目 | 结果 |
| --- | --- |
| phone 到 home 的路径 | 两条直连路径，本机地址 10.82.1.1、10.82.2.1（R87） |
| phone 上 `nexus exec home` 每 20 毫秒一行，断开正在用的 nxl1 | 最长停顿 0.026 秒，命令没有结束（R87） |
| 应用交给核心的系统网络（logcat） | 「网络：eth0」（不计费） |
| `nexus iface` | eth0 不计费（和系统一致）；nxl1、nxl2 系统不知道，按名字不计费（R88） |

redroid 没有蜂窝网络，应用请求蜂窝网络一直挂着、不报错。系统报告「计费」的情形（计费的 Wi-Fi、蜂窝）只有单元测试。
