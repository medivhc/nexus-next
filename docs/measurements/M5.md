# M5 多路径的衡量

脚本：`tools/multipath_check.py`（R56–R61）。机器：云端开发容器，2026-11-19。原始数据：`M5.json`。

## 条件

laptop 和 home 各在一个网络命名空间里，中间两条独立的 veth 链路，各限速 20 Mbit/s（tbf）。
这台机器的内核没有 netem：**链路没有额外延迟**，丢包用 iptables 的随机丢弃模拟。中继关闭。

## 结果

| 项目 | 结果 |
| --- | --- |
| 路径 | 两条直连路径，本机地址分别在两条链路上（R56） |
| 断开正在用的链路（第 1 次 / 恢复后断另一条） | 终端输出最长停顿 43 / 45 毫秒，会话不断（R57）。原来（M5.0）停住直到连接超时，约半分钟后断开 |
| 交互冗余：终端会话输出时各链路的流量 | 31.6 KB / 19.0 KB（两条都走，R58） |
| 一条链路随机丢 30%：终端会话（冗余） | 输出间隔 p99 67 毫秒、最长 71 毫秒 |
| 一条链路随机丢 30%：`nexus exec`（不冗余） | 输出间隔 p99 71 毫秒、最长 103 毫秒 |
| 计费网络：link2 计费时取 16 MB | 16.7 Mbit/s；link2 只承担 0.5%（心跳、确认和交互冗余，R60） |
| 批量分摊：两条都不计费时取 16 MB | 29.8 Mbit/s，一条链路的 1.49 倍；两条链路各约一半（R59） |

（单独多次运行：故障转移的最长停顿 30–260 毫秒；冗余检查另一次是 p99 36 / 54 毫秒、最长 41 / 68 毫秒。）

## 结论

- **断一条不断会话**：从「停住到超时」变成几十毫秒的停顿。关键是三处改动：第一次超时从最早一个未确认的包算起；
  可疑路径上在途的数据立刻在别的路径上重发；每条路径只带自己的确认（否则对的路径会被误判）。
- **交互冗余**：没有延迟的链路上，丢的包很快就被重传，冗余的好处不大（最长间隔 71 对 103 毫秒）；
  往返时间越长，重传越慢，冗余的好处越大。有延迟的链路要在有 netem 的机器上测（GitHub 的 runner）。
- **批量**：两条链路时吞吐是一条的 1.5 倍左右，没有到 2 倍：拥塞控制在每条路径上分别探测带宽，两条链路的排队相互影响；
  后续可以调。计费的链路几乎不承担批量流量。

## 还没测到的

- 有延迟、有抖动的链路（netem）；不同延迟的两条链路（例如有线 5 毫秒、5G 40 毫秒）。
- 真实的蜂窝网络和 Android（手机上的多路径要经 Android 的网络接口 API，阶段 5 之外）。
- 经中继的路径。
