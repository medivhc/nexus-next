# M11.5 功能点：零散的已知限制

对应需求：`FEATURES.md` **R89** 起（编号 R89–R94 留给这一组）。来源：手册第 17 节「已知限制」。

## FP-11.5-01 完整节点和 Android 支持 TCP 半关闭（R89）

### 原因

完整节点和 Android 在虚拟网卡上跑用户态协议栈（ipstack 1.0.1）。它收到程序的 FIN 后立刻替本端也发 FIN、
不等本端写完；读的一方也收不到「对方已关闭」，只能等整条连接结束。于是 `echo hello | nc <地址> <端口>`
这样发完就关闭写方向的程序收不到回应。

### 改法

ipstack 复制到 `vendor/ipstack`，经 `[patch.crates-io]` 替换，改动标注 `NEXUS:`（见 `vendor/README.md`）：

- 收到对方的 FIN（可以带着最后一段数据，也可以和前面的数据分开到）：确认它、进入 CLOSE_WAIT、读方向结束
  （读到 0 字节）；**不**替本端发 FIN。FIN 前面还有没到的数据时先不收这个 FIN，等对方重发。
- CLOSE_WAIT 里本端照常写；本端 shutdown 后，在途数据都被确认时才发 FIN（LAST_ACK）。
- 去掉 CLOSE_WAIT 5 秒后强行发 FIN 的计时：服务慢慢回应也不会被截断。整条连接的空闲超时（60 秒）不变。
- 本端先关闭（FIN_WAIT）后对方的 FIN 到达时，读方向立刻结束，不再等 TIME_WAIT 的 2 秒。
- 连接没有 shutdown 就被丢掉时发 RST，对方不必等超时。

节点这边不用改：入口把程序一侧的「读到结束」转成远端的关闭写方向，反过来也一样（`copy_bidirectional`）。

### 场景

- Given home 发布了回声服务 echo（读到结束后才关闭），laptop 是完整节点
- When laptop 上的程序连 `echo.home.internal`，发 `hello\n` 后关闭写方向
- Then 读到 `hello\n`，随后读到结束
- And 200 KB、跨很多个包的数据同样完整回来
