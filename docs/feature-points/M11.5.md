# M11.5 功能点：零散的已知限制

对应需求：`FEATURES.md` **R89** 起（编号 R89–R94 留给这一组）。来源：手册第 17 节「已知限制」。

## FP-11.5-01 完整节点和 Android 支持 TCP 半关闭（R89）

### 原因

完整节点和 Android 在虚拟网卡上跑用户态协议栈（ipstack 1.0.1）。它收到程序的 FIN 后立刻替本端也发 FIN、
不等本端写完；读的一方也收不到「对方已关闭」，只能等整条连接结束。于是 `echo hello | nc <地址> <端口>`
这样发完就关闭写方向的程序收不到回应。

### 改法

ipstack 复制到 `vendor/ipstack`，经 `[patch.crates-io]` 替换，改动标注 `NEXUS:`（见 `vendor/README.md`）：

- 收到对方的 FIN（可以带着最后一段数据，也可以和前面的数据分开到）：确认它、进入 CLOSE_WAIT、读方向结束
  （读到 0 字节）；**不**替本端发 FIN。FIN 前面还有没到的数据时先不收这个 FIN，等对方重发。
- CLOSE_WAIT 里本端照常写；本端 shutdown 后，在途数据都被确认时才发 FIN（LAST_ACK）。
- 去掉 CLOSE_WAIT 5 秒后强行发 FIN 的计时：服务慢慢回应也不会被截断。整条连接的空闲超时（60 秒）不变。
- 本端先关闭（FIN_WAIT）后对方的 FIN 到达时，读方向立刻结束，不再等 TIME_WAIT 的 2 秒。
- 连接没有 shutdown 就被丢掉时发 RST，对方不必等超时。

节点这边不用改：入口把程序一侧的「读到结束」转成远端的关闭写方向，反过来也一样（`copy_bidirectional`）。

### 场景

- Given home 发布了回声服务 echo（读到结束后才关闭），laptop 是完整节点
- When laptop 上的程序连 `echo.home.internal`，发 `hello\n` 后关闭写方向
- Then 读到 `hello\n`，随后读到结束
- And 200 KB、跨很多个包的数据同样完整回来

### 测试

`crates/nexus-cli/tests/fullnode.rs::half_closed_connections_still_get_their_reply`（只在真实后端：要虚拟网卡）。
Android 用的是同一个协议栈（`nexus_cli::tun::run_stack`），在 redroid 上用 `tools/android_e2e.py` 再验一遍。

## FP-11.5-02 终端会话在设备重启后恢复（R90）

### 原因

M7.2 起会话由独立的持有进程（`nexus session-hold`）管着，常驻程序重启不影响会话；但设备重启时持有进程和
shell 都没了，会话随之消失。

### 改法

- 持有进程每秒（屏幕或尺寸有变化时）把会话状态写到 `<数据目录>/sessions/<会话名>.state`（先写临时文件再改名）：
  格式版本、创建时间、尺寸、shell 的工作目录（Linux 上读 `/proc/<pid>/cwd`）、把终端重绘成当前屏幕的数据。
- 会话真的结束时删掉它：shell 自己退出，或者会话被结束（`session kill`、数据目录被删）。shell 被别的信号结束
  （关机时），或者持有进程收到 SIGTERM、被 SIGKILL 时，留着它。
- 常驻程序启动时（`adopt`）：先接管还活着的持有进程；再对每个有 `.state`、没有活着的持有进程的会话启动一个新的
  持有进程（`--restore`）。新的 shell 在记下的工作目录里启动（目录不在了就用家目录）；屏幕先画记下的内容，
  再加一行「[nexus] 会话已恢复……」。名字和创建时间不变，所以断开的客户端照常接回（不会被当成另一个会话）。
- 格式版本不认识、文件坏了：删掉，不恢复。

### 场景

- Given laptop 连着 home 上的会话 main，在 `~/proj` 里输出过 `before`
- When home 「重启」：常驻程序和持有进程都被 SIGKILL（会话里的 shell 随之结束），然后常驻程序再启动
- Then laptop 上的 `nexus ssh` 自动接回，屏幕上有 `before` 和「会话已恢复」，`pwd` 是 `~/proj`
- And `nexus session ls home` 里 main 的创建时间和重启前一样

## FP-11.5-04 经完整节点转发 UDP（R91）

### 设计

- 发布：`--proto udp`（`SERVICE_PROTOS` 加上 `udp`）。
- 协议 19.5（原定 19.4，合并时 19.4 已被 M10.1 的 `RootRotate` 占用）：新请求 `SvcDatagram { name }`，授权同 `SvcConnect`（`svc.connect@<设备>/svc/<名字>`）。对方回 `Ok` 后
  两个方向都是数据报帧：2 字节大端长度 + 数据报。发布方只对 `udp` 服务接受，对 `tcp`/`http` 服务回
  `InvalidInput`；反过来 `SvcConnect` 连 `udp` 服务时回 `InvalidInput`，说明要经完整节点访问。
- 发布方：`System::udp_connect` 打开一个连上服务地址的 UDP 套接字（仿真里没有 UDP，说不支持），帧和数据报互相转发。
- 完整节点：协议栈交出的每个 UDP 流（源地址+端口 → 目标地址+端口，名字服务除外）交给节点（`TunInbound::Udp`）。
  目标是服务的临时地址时按路由找到服务，开一条 `SvcDatagram` 流转发（服务在本机时直接发给本机的 UDP 套接字）。
- 公网域名命中设备出口时使用 `ExitDatagram`（协议 19.6）。出口必须已经开放并通过 `net.exit` 授权，出口设备负责解析目标。
- 命中 SOCKS5 上游时，通过控制连接协商 `UDP ASSOCIATE`。上游同意后保留目标域名和端口，数据报用 SOCKS5 UDP 头封装。上游拒绝、超时或断开时关闭对应的转发并记录原因。
- 结束：流结束、出错，或两个方向都 60 秒没有数据报（协议栈那一侧 30 秒没有数据报也结束这一路）。
- 数据报不分片：超过一个包的部分被协议栈截掉。

### 场景

- Given home 上有 UDP 回声服务，发布成 game（`--proto udp`），还有 TCP 服务 echo；laptop 是完整节点
- When laptop 上的程序向 `game.home.internal:9000` 发 `hi`
- Then 收到 `echo:hi`；1200 字节的数据报一样完整回来
- And 另一个程序（另一个源端口）发往同一服务的另一个端口，各自收到自己的回应
- And 发往 TCP 服务 echo 的临时地址的 UDP 没有回应

### 测试

- `crates/nexus-cli/tests/fullnode.rs::udp_services_are_reachable_through_the_full_node`（只在真实后端）。
- `nexus-runtime` 的 `datagrams::tests::frames_round_trip_and_end_with_the_stream`：帧的往返、空数据报、流结束时转发结束。
- `nexus-runtime` 的 `public_udp_exit_coexists_with_tcp_and_private_udp` 和 `public_udp_socks_associates_or_closes_without_fallback` 验证三种流量共存及上游拒绝后的行为。
- `nexus-wire` 的 `compat`：19.5 的样例。

## FP-11.5-05 合并保留空目录（R92）

原来合并只看文件和符号链接，合并后的树由这些路径重建，空目录全部丢失。现在合并时把空目录（没有项的目录）
也当作一项参与三方合并（`tree::merge` 里的 `collect_leaves`）：

- base 和两边都有的空目录：保留。
- 一边新建的空目录：保留；一边删掉、另一边没动的：删掉。
- 一边往空目录里放了文件：这个目录不再是「空目录」一项，随文件存在。
- 一边删掉目录里的全部文件、目录本身留着：结果里是空目录。

测试：`crates/nexus-drive-core/tests/history.rs::merge_keeps_empty_directories`（纯逻辑，先红后绿）。

## FP-11.5-06 临时分享列表显示有效、已过期、已用尽与已撤销状态（R93）

### 原因

`nexus share ls` 原来只根据 `revoked` 区分「已撤销」与「有效」，既不按常驻程序的当前时间判断是否超过 `expires_at`，也不区分已达 `--max-uses` 上限的分享；`--json` 输出也没有直接给出是否过期和当前状态字段。

### 改法

- 不改动任何网络协议或本地控制通道消息格式。
- 在纯逻辑层 `nexus-wire` 定义 `ShareStatus`（`Active`、`Expired`、`Exhausted`、`Revoked`）及 `ShareRecord::is_expired(now)`、`ShareRecord::status_at(now)`，优先级与 `validate_share` 一致：已撤销 > 已过期（`now >= expires_at`）> 已用尽（`uses >= max_uses`）> 有效。
- `nexus share ls` 在有分享记录时通过现有 `CtlRequest::Status` 读取本机常驻程序时间 `now`（仿真下即模拟时钟），人类可读输出按状态显示「有效」「已过期」「已用尽」「已撤销」，`--json` 为每条记录追加 `expired` 布尔值与 `state`（`active` / `expired` / `exhausted` / `revoked`）。

### 场景

- Given home 发布了网页服务 web，并创建了四条临时分享：一条 `--ttl 1h`、一条 `--ttl 1s`、一条 `--ttl 1h --max-uses 1`（已被访客打开一次）、一条 `--ttl 1h`（已执行 `nexus share revoke`）
- When 经过超过 1 秒后在 home 上执行 `nexus share ls` 与 `nexus share ls --json`
- Then 人类可读输出中四条记录分别显示「有效」「已过期」「已用尽」「已撤销」
- And `--json` 输出中每条记录保留原有字段，并给出对应的 `expired` 与 `state`（`active`、`expired`、`exhausted`、`revoked`）
- And 对已过期的分享再执行 `nexus share revoke` 后，人类可读输出显示「已撤销」，`--json` 中 `revoked` 为 `true`、`expired` 为 `true`、`state` 为 `revoked`

### 测试

- `crates/nexus-wire/src/lib.rs` 单元测试（纯逻辑，L1）：边界 `now == expires_at`、`uses == max_uses` 与状态优先级。
- `crates/nexus-cli/src/lib.rs` 单元测试：`shares_text` 与 `shares_json` 的四态渲染与字段。
- `crates/nexus-cli/tests/share.rs::share_ls_reports_active_expired_exhausted_and_revoked`（sim + real）。

## FP-11.5-07 一键体检命令 `nexus doctor`（R94）

### 原因

跨网络排障和真机验收时，用户需要分别执行 `nexus status`、`nexus ls`、`nexus path` 和 `nexus route explain` 自己拼凑结论，没有统一的状态汇总和下一步建议。

### 改法

- 不改动网络协议和本地控制通道消息结构，只复用现有的 `CtlRequest::{Status, List, Paths, TunShow, RouteExplain}`。
- 在 `crates/nexus-cli/src/doctor.rs` 用纯数据模型 `CheckStatus`（`Ok < Warn < Fail`）、`CheckItem`、`DoctorReport` 和纯函数 `evaluate` 生成以下检查项：
  - `daemon`：通过 `CtlRequest::Status` 检查本机常驻程序可达性与版本（与命令行版本不一致时降级为 `warn`；不可达时为 `fail` 并直接汇总失败）。
  - `device:<设备名>`（名册中没有其他设备时为 `devices` 告警）：通过 `CtlRequest::List` 检查每台已知远端设备的在线状态，离线标为 `fail`。
  - `path:<设备名>`：对每台在线远端设备，优先读取 `CtlRequest::Paths` 的路径明细（直连/中继、多路径数量、计费标记、最低往返时间），传输层未提供明细时回退到 `ListEntry.report.path` 与 `rtt_ms`；仅有中继或仅有计费路径时为 `warn`。
  - `version`：比较所有在线远端设备的 `NodeInfo.version` 与本机版本，一致为 `ok`，偏旧或偏新时为 `warn` 并给出对应设备的 `nexus upgrade` 建议；没有在线对端时降级为 `warn`。
  - `name_resolution`：结合 `CtlRequest::TunShow` 与 `CtlRequest::RouteExplain`（探测 `probe.<设备>.internal:80`）检查名字解析与 `.internal` 服务路由可用性；完整节点启用时显示内置 DNS 地址，未启用 `--tun` 但 `.internal` 路由正常时说明仅通过统一入口/服务命令解析且保持 `ok`；控制面查询受限或不支持时降级为 `warn`，路由判定异常时为 `fail`。
- 汇总状态 `overall` 取所有检查项的最高严重度（`fail > warn > ok`）。无 `fail` 时退出码为 `0`（含 `warn`），存在 `fail` 时退出码为 `1`。
- `nexus doctor --json` 输出包含 `schema`、`overall` 与 `checks`（每项含 `name`、`status`、`detail`、`suggestion`）的 JSON；人类可读输出逐项展示状态、结论与建议，末尾输出汇总行。

### 场景

- Given 两台设备 `laptop` 与 `home` 已组网且均在线、版本一致、直连通信
- When 在 `laptop` 上执行 `nexus doctor` 与 `nexus doctor --json`
- Then 两次调用退出码均为 0，JSON 中 `overall` 为 `ok`，包含 `daemon`、`device:home`、`path:home`、`version`、`name_resolution` 检查项且每项均含 `name`/`status`/`detail`/`suggestion` 字段，人类可读输出逐行展示检查项并包含汇总行

- Given 上述网络中 `home` 离线
- When 在 `laptop` 上执行 `nexus doctor` 与 `nexus doctor --json`
- Then 两次调用退出码均非 0，JSON 中 `overall` 为 `fail`，`device:home` 的 `status` 为 `fail` 且 `suggestion` 非空，人类可读输出标出失败项与建议

### 测试

- `crates/nexus-cli/src/doctor.rs` 单元测试：覆盖正常、本机常驻程序不可达、未入网、设备离线、仅中继、多路径含计费/全计费、对端版本偏旧/偏新、完整节点 DNS 与数据面降级 `warn`、退出码规则与 JSON/文本渲染。
- `crates/nexus-cli/tests/doctor.rs` 验收场景：`doctor_reports_ok_when_network_is_healthy` 与 `doctor_reports_fail_when_peer_is_offline`（`covers: "R94, R19"`）。

## 不在这一组里

- 挂载只支持 Linux（macOS 要 macFUSE、Windows 要 WinFsp，这里没法验证），硬链接、扩展属性、文件锁：留给跨平台二进制那一组。
- Windows 和 Android 上常驻程序重启时会话结束（没有独立的持有进程）。
- 桌面完整节点的默认路由接管。Android 单 VPN 的接管和按应用选出口见 `docs/android.md`。
