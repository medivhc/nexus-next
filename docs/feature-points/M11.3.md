# M11.3 功能点：macOS 和 Windows 版本

## 模型

- **发布**：推送 `v*` 标签时，除了 Linux 的两个包，还在各自系统的 GitHub runner 上编译：
  - `nexus-<版本>-macos-aarch64.tar.gz`、`nexus-<版本>-macos-x86_64.tar.gz`（在 macOS runner 上编译，Intel 版交叉编译；
    arm64 版在 runner 上运行检查）；
  - `nexus-<版本>-windows-x86_64.zip`：`nexus.exe`（静态链接 C 运行库，不需要另装 VC 运行库）、`wintun.dll`
    （Wintun 0.14.1 的官方预编译版，校验 SHA256 后放进去）和它的许可证 `wintun-LICENSE.txt`。
  - 每个包都有 LICENSE、README.md、manual.md；`SHA256SUMS` 覆盖所有包。
- **平台差异**（代码里的 `cfg` 分叉，核心逻辑不变）：
  - 控制入口：Windows 上本人入口是命名管道、agent 入口是回环 TCP，`ctl.sock` 是写着端点的文件（已有）。
  - 终端会话的持有进程（R84）：Unix 是 `sessions/<名字>.sock` 域套接字；Windows 上 `sessions/<名字>.sock`
    是端点文件，写着回环 TCP 地址和 32 字节的一次性口令（十六进制）。数据目录只有本人能读，连上后先发口令，
    口令不对的连接直接关掉，之后的帧和 Unix 完全一样（持有进程协议版本不变）。持有进程用
    `CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW` 启动：常驻程序被结束或 Ctrl-C 时它不受影响。
  - 升级（R84）：Windows 不能覆盖正在运行的 exe，但可以给它改名。换上：`nexus.exe` 改名为 `nexus.prev.exe`，
    `nexus.new.exe` 改名为 `nexus.exe`；换回：正在运行的 `nexus.exe` 先改名为 `nexus.old.exe`，再把 `nexus.prev.exe`
    改回来（`nexus.old.exe` 在下次升级时删掉）。重新启动：用同样的参数启动新的进程（继承标准输入输出），
    然后本进程退出。`--file` 可以是 `.zip`、`.tar.gz` 或二进制本身；压缩包里找 `nexus` 或 `nexus.exe`。
    Unix 的行为不变（`.prev`、`.new` 后缀，原地 exec）。
  - 虚拟网卡（R83、R81）：
    - Windows：Wintun，网卡名照用户给的；`wintun.dll` 从 `nexus.exe` 所在目录加载，不在时报错说明。
      `.internal` 交给名字服务：PowerShell `Add-DnsClientNrptRule -Namespace .internal -NameServers <名字服务>`，
      带注释 `nexus`；启动时先删掉注释为 `nexus` 的旧规则（上次没正常退出留下的），正常退出时删掉。
    - macOS：utun 只能叫 `utunN`；给的名字不是 `utun` 开头时由系统分配，`nexus status` 里显示实际的名字。
      `.internal` 交给名字服务：写 `/etc/resolver/internal`（`nameserver <名字服务>`），正常退出时删掉。
    - 要管理员权限（Windows 以管理员身份运行，macOS 用 sudo），没有时报错说明。
- **不在 macOS 和 Windows 上的**：挂载（FUSE）、多路径和计费网络识别、`--tun` 的地址段规则（Linux 上也没有）。
- **验证**：用户没有 macOS 和 Windows 设备，所以 CI 在 GitHub 的 macOS 和 Windows runner 上代替真机：
  `tools/platform_check.py` 用编译出的 `nexus` 在 runner 上起两台设备（两个常驻程序，`--local-only`），
  走一遍下面的功能点；runner 上有管理员权限，所以虚拟网卡也真的建。Linux 上同一个脚本也跑（检查脚本本身）。

## FP-11.3-01 发布包（R81、R82）
- Given 推送标签 `vX.Y.Z`
- Then 发布里有 `macos-aarch64`、`macos-x86_64` 的 `.tar.gz` 和 `windows-x86_64` 的 `.zip`；`SHA256SUMS` 覆盖它们
- And 每个包在编译它的 runner 上检查过：`nexus --version` 输出 `nexus X.Y.Z`，`--help` 能运行（Intel 的 macOS 版只检查文件类型）
- And Windows 的包里有 `nexus.exe`、`wintun.dll`、`wintun-LICENSE.txt`；`wintun.dll` 来自 SHA256 校验过的官方压缩包

## FP-11.3-02 两台设备的日常操作（R81、R82）
- Given macOS 或 Windows 上两个常驻程序 laptop、home（`--local-only`）
- When laptop `init`，home `join`，laptop `device approve`
- Then 两边 `ls` 都看到对方在线；两个方向 `status`、`exec`（运行 Python 输出一行）都通
- When home 发布一个本机 HTTP 服务（`--proto http`），laptop `run --use home/<服务>` 里的程序按环境变量访问它
- Then 拿到 200
- When home 当存储设备，laptop 建工作区、写文件、提交，home `drive sync`
- Then home 上读出的内容逐字节相同

## FP-11.3-03 虚拟网卡（R83、R81）
- Given 管理员权限；home 发布了 HTTP 服务 web；laptop 以 `--tun nexus0` 启动
- When `nexus status --json`
- Then 有 `tun`：网卡名（macOS 上是 `utunN`）、网段、名字服务的地址
- When 直接向名字服务的地址发 DNS 查询 `web.home.internal`（A）
- Then 得到网段里的一个地址；不设代理连这个地址的 80 端口发 HTTP 请求，拿到 home 上服务的回应
- When 用系统的名字解析查 `web.home.internal`
- Then 得到同一个地址（Windows：NRPT 规则；macOS：`/etc/resolver/internal`）
- When laptop 的常驻程序被结束（不是正常退出，规则留下了），再以 `--tun` 启动
- Then 注释为 `nexus` 的 NRPT 规则只有一条（启动时先删旧的，不会越积越多）；macOS 上 `/etc/resolver/internal` 照常

## FP-11.3-04 会话在常驻程序重启后还在（R84、R66）
- Given laptop 上 `nexus ssh home`（标准输入输出是管道）连着会话 main，让 shell 输出一行标记
- When home 的常驻程序被结束再启动
- Then 会话还在：`session ls home` 的 `created_at_ms` 不变；之后输入的命令照常输出
- And 持有进程的连接：在每个平台上，常驻程序断开后能重新连上，结束会话后端点文件被删掉
  （`crates/nexus-sys-real/tests/holder_transport.rs`，Windows 上口令不对的连接被拒绝）

## FP-11.3-05 Windows 上升级与换回（R84）
- Given home 的常驻程序在运行，用的是复制出来的一份二进制
- When `nexus upgrade --file <同一版本的 .zip 或 nexus.exe>`
- Then 回答是 `pending`，常驻程序重新启动（启动时间变了），几秒内 `upgrade --status` 是 `confirmed`；
  `nexus.prev.exe` 是原来的那份
- When `nexus upgrade --rollback`
- Then 状态 `rolled_back`（原因：手动），常驻程序又重新启动，`nexus.exe` 和升级前逐字节相同
- And 文件不是 nexus：退出码 107，常驻程序没有重启（同 FP-7.3-02）

## 测试方式

- `crates/nexus-cli/src/upgrade.rs` 的单元测试：各平台的文件名（`.prev`/`nexus.prev.exe`）、`.zip` 和 `.tar.gz` 里
  找 `nexus`/`nexus.exe`、Windows 的换上和换回顺序（在所有平台上按 Windows 的顺序走一遍）。
- `crates/nexus-sys-real/tests/holder_transport.rs`：持有进程的连接（每个平台）。
- `tools/platform_check.py`：FP-11.3-02 到 05，在 CI 的 macOS、Windows runner（和 Linux）上跑；
  虚拟网卡部分要管理员权限，`--tun` 参数打开。
- 发布流程（FP-11.3-01）：`.github/workflows/release.yml`，手动运行不带标签时只编译检查、不发布。
