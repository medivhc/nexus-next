# M7.1 功能点：新旧版本互通

## 模型

- 协议版本分主版本和次版本，写作 `19.0`。主版本变了才不兼容（连接的协议名也跟着变：`nexus/rpc/5`）；
  次版本只增加东西：新的请求、新的回应、新的错误码。
- 请求头带发送方的主版本、次版本；请求体单独编码。收到不认识的请求体时，回应「本机版本较旧，不认识这个请求」，
  而不是断开。回应也单独编码、带次版本；不认识的回应同样报告对方版本较新。
- 已有的请求、回应的编码永远不变。`crates/nexus-wire/tests/fixtures/` 存着每个次版本的每种消息的编码，
  测试检查当前代码编码出来的和存着的逐字节相同、存着的都能解码。
- 错误码以后会增加：不认识的错误码当作「未知错误」，说明照常显示。
- 规则写在 `docs/protocol.md`。

## FP-7.1-01 已有消息的编码不变（R65）
- 每个请求、回应、错误码、请求头、回应信封都有一个样例；样例的编码和 fixtures 里 19.0 的逐字节相同
- fixtures 里的每一条都能解码成同一个样例
- 新增一个请求或回应却没有样例时编译不过（样例表按穷举匹配）

## FP-7.1-02 不认识的请求（R65）
- Given home 是旧的次版本，收到一个它不认识的请求（编码里的请求种类超出它的范围）
- Then home 回应错误：版本较旧，消息里有 home 的版本和双方的协议次版本；连接不断，之后的请求照常
- And 请求方的命令以这个错误退出，说明是对方需要升级

## FP-7.1-03 不认识的回应和错误码（R65）
- 回应信封里的回应体本机不认识：报告对方版本较新（协议次版本），不当作内部错误
- 错误码本机不认识：当作「未知错误」，对方给的说明原样显示

## FP-7.1-04 能看到各设备的版本（R65）
- `nexus ls --json` 每台在线设备有 `version`（例如 `0.2.0`）；和本机不同时 `version_differs` 为 true
- 文本输出里版本不同的设备后面标出它的版本

## FP-7.1-05 主版本不同（R65）
- 旧主版本的设备连过来：协议名不同，连接建立不起来；`nexus status <设备>` 报「版本不兼容」或连不上（不是内部错误）

## FP-7.1-06 真实的新旧混跑（R65）
- `tools/compat_check.py --old-bin <上一个发布版本>`：laptop 用新版本、home 用旧版本（以及反过来），
  ls、status、exec、发布和使用服务、drive 同步都成功
- GitHub 的 CI 里，有同一主版本的发布标签时构建它跑这项检查；没有时跳过并说明

## 测试方式

单元测试 `crates/nexus-wire/tests/compat.rs`（fixtures）、`nexus-runtime` 的单元测试（不认识的请求），
验收场景（`ls` 的版本），`tools/compat_check.py`（真实的两个版本）。
