# M7.3 功能点：升级与回滚

## 模型

- `nexus upgrade --file <压缩包或二进制>`：本机的常驻程序换成新版本。压缩包是发布流程生成的 `.tar.gz`；
  旁边有 `SHA256SUMS` 时校验它。从网上下载交给浏览器或 `curl`（仓库是私有的，下载要登录）；
  从一台设备把新版本推给其他设备见 M7.3b（`--to`、`--all`）。
- 常驻程序做这些事（命令行等它回答）：
  1. **检查**：解出 `nexus`；`nexus --version` 能运行；`nexus protocol-version` 的主版本和本机相同（不同时要 `--force`）；
     `nexus daemon --preflight` 能读本机的数据目录。任何一步不过：不换，回答原因（107）。
  2. **换**：新版本写到 `<二进制>.new`，原来的改名为 `<二进制>.prev`，`.new` 改名为二进制（同一目录里改名，是原子的）。
     没有写权限时不换，说明原因。
  3. **记下**：数据目录的 `upgrade.json`：从哪个版本到哪个版本、升级前在线的设备、确认期限、状态 `pending`。
  4. **重新启动**：回答命令行之后，用同样的参数执行新的二进制（进程号不变，systemd 照常管理）。
- 新版本启动时看到 `pending`：
  - 启动次数加一；超过 3 次（反复崩溃，被 systemd 拉起）：换回 `.prev`，状态 `rolled_back`。
  - 升级前没有在线的设备：直接 `confirmed`。
  - 否则每 2 秒查一次那些设备；期限内（默认 60 秒，`--confirm-within`）连上一台：`confirmed`；
    到期还连不上：换回 `.prev`，状态 `rolled_back`，原因写进 `upgrade.json`，用原来的版本重新启动。
- `nexus upgrade --status`：最近一次升级的状态。`nexus upgrade --rollback`：手动换回 `.prev` 并重新启动。
- 只在 Unix 上；Windows 上报告不支持。

## FP-7.3-01 升级并确认（R67）
- Given home 的常驻程序在运行，laptop 在线，laptop 上 `nexus ssh home` 连着会话
- When home 上 `nexus upgrade --file <新的二进制>`
- Then 回答里有原来和新的版本；常驻程序重新启动（启动时间变了），几秒内 `nexus upgrade --status` 是 `confirmed`
- And 二进制是新的那个，`<二进制>.prev` 是原来的；laptop 上的终端会话还能用

## FP-7.3-02 检查不过（R67）
- 给的文件不是 nexus（例如一个只输出别的东西的脚本）：退出码 107，说明哪一步不过；常驻程序没有重启，二进制没有变
- 文件不存在：107

## FP-7.3-03 连不上网络就换回（R67）
- Given 新版本启动后连不上任何设备（测试里用 `NEXUS_TEST_NO_NETWORK=1` 让它不用任何网络）
- When `nexus upgrade --file <它> --confirm-within 4s`
- Then 4 秒后自动换回原来的版本并重新启动；`nexus upgrade --status` 是 `rolled_back`，原因写着连不上；
  二进制和升级前的逐字节相同；laptop 又看得到 home 在线

## FP-7.3-04 手动换回（R67）
- 升级确认之后 `nexus upgrade --rollback`：换回 `.prev`，重新启动，状态 `rolled_back`（原因：手动）
