# M5.1 功能点：多条路径与故障转移

## 模型

- 传输层（iroh、noq 的分支，见 `vendor/README.md`）对一台设备只有一条 QUIC 连接，连接里有多条**路径**：
  每条路径是「本机的一个地址 → 对方的一个地址」，经中继的路径另算。
- 本机每个网络接口的地址都打洞、都留一条直连路径；直连路径都是可用的（按各自的发送余量排包），中继只在没有直连时用。
- 包从源地址所在的接口发出（一个套接字上，不同路径走不同接口）。
- **故障转移**：一条路径上的包一段时间没有确认（第一次超时从最早一个未确认的包算起，约几个往返），
  而别的路径还好时：这条路径上在途的数据立刻在别的路径上重发，这条路径之后只发探测；探测得到确认就恢复使用。
  每条路径只带它自己的确认，所以路径的好坏两个方向都看得出来。
- 每条路径每秒一次心跳；5 秒没有回应就放弃这条路径；之后每 5 秒检查一次，本机地址没有路径就重新打洞。
- `nexus path [设备]`：每台连着的设备的每条路径：本机地址、对方地址、直连还是中继、往返时间、收发字节数、丢包数。

## FP-5.1-01 多条网络都用上（R56）
- Given laptop 和 home 之间有两条独立的链路（不同网段）
- When 两台设备组网，laptop 上执行一个持续输出的远端命令
- Then `nexus path home` 列出两条直连路径（本机地址分别在两条链路上），往返时间都有值
- And 两条链路上都有流量（至少有心跳）

## FP-5.1-02 断一条，会话不断（R57）
- Given 同上，命令每 20 毫秒输出一行
- When 丢弃正在用的链路上的所有包（接口不 down）
- Then 输出在 1 秒内恢复（最长停顿不超过 1 秒），命令没有结束
- When 恢复这条链路，过一会儿再丢弃另一条
- Then 同样 1 秒内恢复：恢复的链路被重新用上了

## FP-5.1-03 可解释（R56）
- `nexus path` 不带设备时列出所有连着的设备；`--json` 输出 `devices[].paths[]`，每条路径有
  `local`、`remote`、`kind`（direct / relay）、`rtt_ms`、`tx_bytes`、`rx_bytes`、`lost_packets`
- 没有连接的设备：`paths` 为空，文字输出写「没有连接」

## 测试方式

多路径要真实的网络接口和内核：`tools/multipath_check.py`（网络命名空间、两条 veth 链路、iptables 丢包），
需要 root；CI 里用 sudo 运行。仿真后端没有多路径。

## 结果（2026-11-19，开发容器，两条不限速的 veth 链路）

连续三次：两条链路都有直连路径；断开正在用的链路，输出的最长停顿 30–60 毫秒，会话不断；
恢复后重新用上，再断另一条同样。原来（M5.0）一条路断了会话停住直到连接超时。

交互流量量小，数据都在第一条路径上（noq 按发送余量排包，第一条一直有余量），另一条只有心跳。
交互流量两条都发是 M5.2 的冗余；批量按容量分摊是 M5.3。
