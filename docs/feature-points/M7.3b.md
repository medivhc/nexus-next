# M7.3b 功能点：从一台设备升级其他设备

## 模型

- `nexus upgrade --file <压缩包或二进制> --to home[,work…]`，或者 `--all`（除本机外所有在线的设备，按名字排序）。
  本机不升级；要连本机一起升级，最后再运行一次不带 `--to` 的 `nexus upgrade --file`。
- 本机先校验文件（旁边有 `SHA256SUMS` 时），然后对每台设备依次：
  1. **问状态**：在那台设备上执行它自己的 `nexus upgrade --status`，记下最近一次升级的编号。
     做不到时报告原因：设备离线或不存在、没有执行命令的权限、那台设备的版本较旧（还没有这项功能，110）。
  2. **送过去并升级**：经 Nexus 的执行命令把文件送到那台设备的数据目录，在那里执行 `nexus upgrade --file`，
     检查、换上、重新启动都按 R67。检查不过：这台设备什么都不改，报告原因（107），继续下一台。
  3. **等结果**：每秒问一次状态，直到出现新的那次升级的结果（`confirmed` 或 `rolled_back`）；
     最多等确认期限加 30 秒，等不到报告超时（124）。
  - 一台换回了：后面的设备不再升级，标为 `skipped`。
- 能这样做靠两件事：常驻程序执行的命令带着 `NEXUS_EXE`（常驻程序自己的二进制）和 `NEXUS_DATA_DIR`
  （它的数据目录），在那台设备上执行的 `nexus` 命令就找得到那里的常驻程序；每次升级有编号（`id`，
  换上的时间），`nexus upgrade --status` 回答里带着，用来区分新旧两次升级。
- 权限：调用者要能在目标设备上执行命令（本人的设备都可以；agent 按它的授权）。
- 输出：每台设备一行（`--json` 时是 `devices` 数组，每项有 `device`、`state`、`from`、`to`、`message`）。
  `state`：`confirmed`、`rolled_back`、`failed`、`timed_out`、`skipped`。
  退出码：全部确认为 0；否则是第一台没确认的设备的原因（检查不过 107、换回 106、超时 124、版本较旧 110 等）。

## FP-7.3b-01 升级另一台设备（R68）
- Given laptop 和 home 在同一网络，laptop 上 `nexus ssh home` 连着会话
- When laptop 上 `nexus upgrade --file <新的二进制> --to home`
- Then 命令结束时 home 是 `confirmed`，回答里有原来和新的版本；home 的常驻程序重新启动过，二进制的原版留作 `.prev`
- And laptop 上到 home 的终端会话还能用；laptop 自己没有升级

## FP-7.3b-02 检查不过（R68）
- 给的文件不是 nexus：home 是 `failed`，原因说哪一步不过，退出码 107；home 没有重新启动，二进制没有变
- `--to` 里的设备不存在：那台 `failed`，退出码 103

## FP-7.3b-03 所有设备，一台换回就停（R68）
- Given laptop、home、work 在同一网络
- When laptop 上 `nexus upgrade --file <启动后连不上网络的版本> --all --confirm-within 4s`
- Then 先升级 home（名字在前）：换回了，状态 `rolled_back`，原因写着连不上；work 是 `skipped`，二进制没有变；
  退出码 106

## FP-7.3b-04 所有设备都确认（R68）
- `--all` 给正常的新版本：home 和 work 都是 `confirmed`，退出码 0

## 测试方式

验收场景 `crates/nexus-cli/tests/upgrade.rs`（只在真实后端；被升级的设备各用一份自己的二进制）。
「版本较旧」没有自动测试：要一个还没有这项功能的旧版本。旧版本执行的命令不带 `NEXUS_EXE`，送过去的命令检查到就以 110 退出。
