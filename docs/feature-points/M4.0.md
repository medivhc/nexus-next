# M4.0 技术验证（Drive）

探针：`tools/drive-probe`（不属于产品代码）。机器：云端开发容器，2 核，2026-11-18。

## 1. FUSE 可用

- 开发容器：有 `/dev/fuse`、`fusermount3`（fuse3 3.14），root 下 `fuser` 0.15 挂载成功。
- Rust 一侧用 `fuser`（纯 Rust，不需要 libfuse 开发包，挂载时调用 `fusermount3`）。
- GitHub 的 runner：在 M4.3 的 CI 里确认（ubuntu-24.04 自带 fuse3）。

## 2. 在挂载目录里构建的开销

只读透传（每个请求转到真实文件，属性缓存 60 秒），在挂载目录里 `cargo check -p nexus-runtime`，
目标目录放在挂载之外（构建产物不进工作区）：

| | 本地目录 | FUSE 挂载 |
| --- | --- | --- |
| 冷构建（依赖在 cargo 缓存里，不经挂载） | 80.3 秒 | 73.2 秒 |
| 没有改动的检查 | 0.19–0.25 秒 | 0.21–0.25 秒 |

结论：读路径的开销在噪声以内；构建的主要成本不在源文件读取。

**发现**：属性缓存 60 秒时，在挂载之外改了文件（`touch`），挂载里看到的还是旧的修改时间，cargo 认为不用重编。
Drive 的挂载里，本地写入经过挂载本身，不受影响；但同步进来的新提交必须主动让内核丢掉旧的属性和页面
（FUSE 的 inval 通知），否则程序看到旧内容。M4.3 的场景要覆盖这一点。

## 3. 分块与哈希的吞吐

FastCDC（v2020，最小 16 KiB、平均 64 KiB、最大 256 KiB）+ BLAKE3，单线程：

| 数据 | 大小 | 块数 | 速度 |
| --- | --- | --- | --- |
| 一个 512 MiB 的随机文件 | 537 MB | 6734 | 650 MB/s |
| cargo 的源码缓存（35349 个小文件） | 805 MB | 40144（不同的 33868） | 25 MB/s，瓶颈在逐个读小文件 |

结论：分块和哈希不是瓶颈；导入大量小文件时瓶颈是文件系统，之后可以并行读。
选定参数：FastCDC 16/64/256 KiB；小于最小块的文件是一个块；哈希用 BLAKE3（32 字节）。
