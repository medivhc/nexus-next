# M10.1 功能点：根密钥轮换（无需重建网络）

对应需求：`FEATURES.md` **R75**（并遵循 **R01**、**R12**、**R18**、**R64**）。

## 设计要点

1. **为什么需要根密钥轮换**：
   - 当建网时打印的恢复码不慎泄露，或曾作为管理设备的机器丢失/通过 `nexus recover` 转移管理权后，旧根私钥可能已被外部掌握。
   - 若不轮换根密钥，持有旧恢复码的人仍能再次执行 `nexus recover` 夺回管理权，或伪造新名册与 Agent 证书。
2. **双签名根密钥交接证书（`SignedRootRotation`）**：
   - 用途隔离：在 `nexus-core-proto::crypto::Purpose` 中新增 `RootRotation`（标签 `nexus/v1/root-rotation\0`）。
   - `RootRotation { old_root, new_root, version }` 绑定旧根公钥、新根公钥以及切换时的名册版本号（严格大于当前名册版本），由**旧根私钥**签名生成 `old_sig`，同时配套的主名册（`roster.root = new_root, roster.version = version`）由**新根私钥**签名。
   - 任何持有 `old_root` 的设备收到 `Request::RootRotate`（或离线重连同步）时，调用 `verify_root_rotation(&trusted_root, current_roster, &rotation, &new_roster)` 同时校验：
     1. `rotation.old_root == trusted_root` 且 `old_sig` 通过 `trusted_root` 验证；
     2. `new_roster.roster.root == rotation.new_root`、`new_roster.roster.version == rotation.version` 且严格大于当前名册版本；
     3. `new_roster` 通过 `new_root` 验证且内容自洽。
   - 验证通过后，设备原子更新本地 `KEY_ROOT_PUB`、`KEY_ROSTER` 与轮换链 `KEY_ROTATIONS`，若是旧管理设备但不再是新名册的 `Admin`，自动清除本地失效的 `KEY_ROOT_KEY`。
3. **旧恢复码与旧根签发物立即失效，离线设备自动追赶**：
   - 轮换后，管理设备生成并返回新的 64 位十六进制恢复码；拿旧恢复码在任何已更新设备上执行 `nexus recover` 均被拒绝（`恢复码不属于这个网络`）。
   - 旧根签发的 Agent 证书在已更新设备上立即因 `CertBadSignature` 被拒绝，正在运行的旧 Agent 终端连接也会因 `roster_epoch` 变更立即断开；新根签发的 Agent 正常通行。
   - 轮换期间离线的设备在恢复通信、触发名册落后（`StaleRoster`）时，已更新设备会先将缓存的 `RootRotation` 链推过去，使其平滑追赶到新根而无需重新 `join`。
4. **Vault 条目随根重新加密**（与 M9.2 的交互）：
   - Vault 密文用「根密钥 × 设备密钥」协商出的密钥加密。轮换时管理设备先在内存里把全部条目从旧根重新加密到新根，
     和新根一起落盘（任何一条解不开就放弃轮换），然后按新根把条目重新推送给在线的被授权设备。
   - 轮换时离线的设备追上新根后，运行一次 `nexus vault sync` 即可重新读到条目。
